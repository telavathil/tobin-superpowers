The idea: AI-written code drifts toward the same habits: defensive guards for impossible values, invented defaults, comments narrating the change, copy-pasted helpers, casts in tests. These standards name those habits and ban them at the earliest point, when the plan is written. By the time code exists, every task already carries the rules.

How it works

  1. You start a plan as usual with superpowers:writing-plans (or any skill named plan).
  2. A PreToolUse hook on the Skill tool notices the plan skill and injects the standards into Claude's context. Claude Code moves any single hook's context over 10,000 characters to a file, so the hook runs as two commands, each about 7K: part 1 has the obligations, the index and the first half of the standards, and part 2 has the rest.
  3. Claude writes the plan against the standards. Every code block must comply, and the binding rules of each applied standard are copied verbatim into the plan's Global Constraints section.
  4. On the first plan in a repo, part 2 also tells Claude to run the lint baseline check, ask where out-of-scope work is tracked, and record the result. Later plans get the recorded state instead.
  5. Implementers and reviewers only ever see the plan, and the rules are in it.
  6. Separately, whenever Claude runs an install command, a Bash hook checks the package against the manifest and asks you if it is new.

Both hooks only inform or ask. They never block a tool call and always exit 0.

The 11 standards

Each standard is a short Markdown file in standards/global/: a principle, Forbidden and Allowed lists, and a // no / // yes example. The core rules are summarised below.

Trust the types trust-types.md

Validate untyped data once, where it enters. After that, trust the type.

  • Validate at entry points: HTTP input, loose DB fields, queue payloads, third-party responses, env vars, files.
  • Everywhere else: no runtime checks for values the type rules out, no tests that cast to reach them, no hand-written type guards for data that already has a schema, no identity maps.
  • Exhaustiveness goes through a never check, so the compiler proves it with no test needed.

Type safety (TypeScript) type-safety.md

Applies to new and changed lines only.

  • Forbidden: any, as Type (including as never), !, @ts-ignore, @ts-expect-error, eslint-disable.
  • Prefer discriminated unions over objects with many optional fields.
  • Exceptions: as const, and partial mocks of large framework types in specs.
weak
type Actor = { kind: 'user' | 'system';
  userId?: string; service?: string };
strong
type Actor =
  | { kind: 'user'; userId: string }
  | { kind: 'system'; service: string };

Fallbacks fallbacks.md

Required values fail fast. Don't invent defaults.

  • Forbidden: ?? 'default' on always-present values, catch {} that swallows errors, returning [] / null to hide a missing upstream value.
  • Allowed: defaults the spec or API contract defines, and genuinely optional legacy data typed as field?: T.

Edge cases edge-cases.md

At plan time, list the easy-to-miss inputs each changed function's type allows.

  • Inputs that real callers or data can reach get handling and a test. Inputs nothing reaches are noted, not tested.
  • A wrong type (any, a required field real data omits, two copies of a type that disagree) gets fixed where the data enters, not guarded downstream.
no
const first = orders[0].id
// orders can be empty
yes
const first = orders.at(0)
if (!first) throw new Error('order list is empty')

Comments comments.md

Default: no comment. A comment must explain a why that stays true as long as the code does.

  • Forbidden: narrating the change, ticket or time scope, file:line pointers, defending a review fix, restating the code, arithmetic and labels in tests.
  • No ticket IDs, Task N or Step N anywhere in code: not in test names, errors, logs or constants. The one exception is // WARN: remove once PROJ-123 lands.

Reuse before writing reuse.md

Search for an existing helper, type, constant or wrapper before adding one.

  • Derive types (keyof, Pick, Extract) instead of redeclaring them. No one-line forwarding wrappers, no hand-kept lists that mirror a registry, and two functions with the same body are one function.
  • Limit: share code that changes for the same reason, not code that only looks alike.

Compatibility shims shims.md

When renaming or removing, update every caller in the same change and delete the old form.

  • Forbidden: alias exports, parameters widened to take both old and new shapes, dead "compat" fields, deprecated forwarders, **kwargs sinks.
  • Allowed only for callers that can't be updated, and the comment must name them.

Testing testing.md

Shared typed builders, literal expected values, no casts on domain data.

  • One builder per domain object, taking Partial<T> overrides. Extend an existing builder before writing a new one.
  • Assert literal values. Put the meaning in the test name, not in a comment, and never re-implement the formula under test.

Logging logging.md

Log once per operation, at the outcome.

  • No "starting X" / "X succeeded" pairs. Success logs go at debug level.
  • Errors are logged once, where they are handled, with the IDs needed to investigate, and not at every layer they pass through.

Dependencies and APIs dependencies.md

Check an API against the installed version, not memory.

  • Read the installed types or source. Before adding a package, check what is already installed, vet the registry entry (publisher, downloads, repository) and say why the package is needed.

Plan code plan-code.md

Plan code is copied verbatim by implementers, so it must be final code. More below.

Lint baseline check

On the first plan in a repo, Claude compares each lint config the plan touches with a baseline. A monorepo can have several configs. It reports gaps in one message, offers a separate gap PR so the feature plan stays clean, and asks once for the repo's debt location (usually Jira). All rules are error, never warn, and existing violations are frozen by a ratchet so only new code is held to the baseline.

LanguageToolKey rulesRatchet
TypeScriptESLint ≥ 9.24, flat config, typed linting no floating or misused promises, no any, no unused vars; function ≤ 75 lines, complexity 15, params 4, depth 4 eslint --suppress-all → committed eslint-suppressions.json
Gogolangci-lint v2 errcheck, funlen (75 lines / 50 statements), gocyclo 15, revive, govet, staticcheck issues.new-from-merge-base: main
Pythonruff + basedpyright E, F, B, blind except, silent try/except/pass, ANN, complexity 15, args 5, statements 50; reportAny ruff --add-noqa + basedpyright --writebaseline

Possible statuses: baseline gap PR offered can't ratchet (ESLint < 9.24) typed lint too slow. If one-file typed lint takes over 5s, the two promise rules are left out.

The result is written to a per-repo marker file in the plugin's data folder:

~/.claude/plugins/data/tobin-superpowers-tobin-superpowers-dev/repos/<repo-path-with-dashes>.md

New-package prompt

LLMs sometimes invent plausible package names, and attackers register them ("slopsquatting"). Before an install command runs, a Bash hook reads it and asks you to confirm any package that isn't in the nearest manifest. It only ever answers ask: it never blocks or approves a command, and if the check itself fails, it asks.

CommandsChecked against
npm i / install / add, pnpm add, yarn addpackage.json (all dependency sections)
go getgo.mod (subpackages of a listed module count)
pip install, python -m pip, uv add, uv pip install, poetry addpyproject.toml and requirements*.txt

It handles chained commands, sudo / env / NAME=value prefixes and Python name normalisation.

Project overrides. A repo can add its own agent-os/standards/. Those add to the global standards, and where they conflict, the project's version wins.

Known gaps

  • The package prompt doesn't cover npx, bunx, uvx, pipx, go install, bun add or yarn global add. npx / uvx / bunx run a package immediately and are the first follow-up.
  • It reads the manifest from the session's folder, so a cd earlier in the same command isn't followed. It also skips commands wrapped in bash -c, time or nohup.
  • Standards are injected as instructions. The model is told to follow them, and the lint baseline enforces what tooling can, but nothing mechanically checks every plan against every rule.
